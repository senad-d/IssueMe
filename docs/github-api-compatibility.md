# GitHub API compatibility

IssueMe pins REST requests to `X-GitHub-Api-Version: 2022-11-28` (`GITHUB_API_VERSION` in `src/constants.ts`) and sends `GraphQL-Features: sub_issues` on `/graphql`. This document separates what GitHub documents from what IssueMe has tested, so a documented endpoint is never mistaken for a verified one. Reviewed against docs.github.com on 2026-10-09.

Evidence levels used below:

- **Documented**: the public GitHub documentation describes the endpoint or mutation. This does not prove the token, repository, or organization can use it.
- **Mocked**: `test/` covers the request shape and response handling with an injected `fetch`; no network access.
- **Live**: an operator ran the opt-in plan in [`live-github-verification.md`](live-github-verification.md) and recorded the result. No row is marked live unless such a run is recorded.

## REST version decision

| Version | Documented support | IssueMe use |
| --- | --- | --- |
| `2022-11-28` | Supported until 2028-03-10; used for requests without a version header. | Pinned (`GITHUB_API_VERSION`). |
| `2026-03-10` | Current; end of support not yet scheduled. | Not adopted. |

Decision: keep `2022-11-28`.

- The documented `2026-03-10` breaking changes that touch issue endpoints remove the singular `assignee` response field and deprecate the `beta` media type and the default `pull_request` property. IssueMe reads `assignees` arrays, requests `application/vnd.github+json`, and detects pull requests with a null/undefined check, so none of these blocks IssueMe on either version. They are also not a reason to move.
- GitHub documents versions as behavior switches for breaking changes, not as gates for new endpoints. The dependency, related-issue, timeline, and issue-type endpoints below are additive paths. The `2026-03-10` header in their examples is the documentation default, not a stated minimum.
- A version change without live regression coverage would alter behavior for every existing tool at once. Unresolved compatibility is therefore scoped to the affected feature: a tool whose endpoint GitHub rejects reports that failure for that tool only.

Regression coverage: `test/github-transport-client.test.mjs` asserts the pinned header value, that it is listed in `GITHUB_DOCUMENTED_API_VERSIONS`, and that the `sub_issues` GraphQL feature flag is sent only to `/graphql`. Changing the pin requires updating that list, this document, and re-running the live plan.

## Unknowns

- Whether the dependency, related-issue, timeline, and issue-type endpoints respond identically under `2022-11-28` and `2026-03-10`. Documentation does not gate them by version; only a live run can confirm.
- Fine-grained permission names for dependency and related-issue mutations. The documentation lists status codes, not permissions.
- Whether the `issue_dependencies_summary` object on issue responses is present under `2022-11-28`.
- GitHub backlog sync during planning failed with `401 Unauthorized`. Nothing here is validated against the live repository.

## Review procedure

1. Re-read the references listed under "Authoritative API references" in `specs/spec-issue-management-gap-tasks.md`.
2. Update this table and `GITHUB_DOCUMENTED_API_VERSIONS` when GitHub publishes or retires a version.
3. Run `npm run validate`. Run the live plan only with explicit authorization and disposable fixtures, then record each affected row as live-verified, unavailable, or still unverified.
